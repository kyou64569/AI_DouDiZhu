> 文档版本：v1.0

## 1. 产品目标

**一句话价值主张：**
让普通用户无需编写代码，即可用自己拥有的任意大模型 API，配置并体验"可自定义、可参与、可观看"的 AI 斗地主对局。

**3 条核心目标：**

- **G1｜零代码多模型接入**：支持添加多个大模型配置（API Key + Base URL），一键动态拉取服务商可用模型列表，用户可灵活切换不同模型驱动 AI 玩家。
- **G2｜双模式覆盖参与与观赏**：提供"人机对战"（用户+2 AI）与"纯 AI 观战"（3 AI 自动对战）两种模式，覆盖"亲自博弈"与"观赏娱乐"两类需求。
- **G3｜完整规则 + 可解释 AI**：内置完整合规的斗地主规则引擎，AI 出牌由大模型决策并展示思考过程，对非法出牌做合法校验与兜底，保证对局公平、过程可看懂。

## 2. 用户故事

> 每条故事均含验收标准（AC），作为下游验收依据。

### US-1 模型配置
**作为**普通用户，**我希望**能添加并保存多个大模型的 API Key 与 Base URL，并能一键拉取该服务下的可用模型列表，**以便**我无需编码即可灵活切换不同模型来驱动 AI 玩家。

- AC1：可新增 / 编辑 / 删除模型配置，字段至少包含：配置名称、Provider 名称、Base URL、API Key。
- AC2：点击"拉取模型"可调用该服务模型列表接口（OpenAI 兼容 `/v1/models` 或等价接口），返回模型列表供用户勾选 / 搜索。
- AC3：提供"连通性测试"按钮，返回成功 / 失败状态及响应延迟（ms）。
- AC4：所有配置持久化保存，应用重启后仍然存在。

### US-2 AI 玩家管理
**作为**用户，**我希望**创建多个 AI 玩家，每个绑定一个已配置的模型并自定义名称，**以便**在对局中安排不同模型 / 性格的对战组合。

- AC1：可新增 / 编辑 / 删除 AI 玩家，字段至少包含：玩家名称、绑定的模型配置（下拉选择）、可选备注 / 头像。
- AC2：列表页展示全部 AI 玩家及其绑定的模型名称。
- AC3：不能删除 / 编辑"正在房间中使用的玩家"，若尝试需给出明确阻断提示。

### US-3 房间创建
**作为**用户，**我希望**创建一个房间并指定 AI 玩家入座（人机模式我占一席；观战模式三席均为 AI），**以便**发起一局对战。

- AC1：创建房间时须选择模式（人机 / 观战）。
- AC2：人机模式——用户为固定玩家（不占可选 AI 位），需从 AI 玩家列表选 2 个入座；观战模式——需选 3 个 AI 入座。
- AC3：座位满员后"开始游戏"按钮才可用。
- AC4：房间为本地单用户概念，**无多端联机**（仅本机对局，详见决策 D1）。

### US-4 人机对局
**作为**用户，**我希望**以玩家身份与 2 个 AI 斗地主，由我手动出牌、系统驱动 AI 出牌，**以便**体验"我 vs AI"的博弈。

- AC1：发牌后我能看到自己的 17 张手牌与 3 张底牌（叫到地主后明牌，见 D5）。
- AC2：我能进行叫分 / 抢地主（本产品采用叫分制，见 D2）、出牌 / 不出（过）操作。
- AC3：AI 回合自动决策并出牌，返回非法时自动兜底（见 REQ-R8）。
- AC4：完整回合流转直至一局结束并结算积分（见 D3）。

### US-5 观战
**作为**用户，**我希望**仅观看 3 个 AI 自动对战，**以便**学习或娱乐观赏，无需我任何操作。

- AC1：进入观战房间后无需任何操作，对局自动推进。
- AC2：实时展示三方出牌、地主标识、思考日志面板（REQ-U2）。
- AC3：一局结束自动展示结算，并提供"再来一局"。

## 5. 关键产品决策（已拍板，下游无需再猜）

### D1 数据持久化范围：是否需要后端？
- **决策：纯前端单机应用，不设独立后端。** 模型配置、AI 玩家、战绩等全部存于浏览器本地存储（localStorage / IndexedDB，具体由架构定）。
- **API Key 存储**：明文存于本地存储（单机、不外传）；PRD 要求首次使用时弹窗明确告知"密钥仅存于本机浏览器，请不要在公共设备使用"，并提供"显示/隐藏"切换。**加密存储列为 P2（REQ-P2-1）**，不在首版强制。
- **大模型调用方式**：前端直接调用各 Provider 的 OpenAI 兼容 Chat Completions 接口。若某 Provider 不支持浏览器跨域（CORS），由架构层评估"轻量本地代理 / 允许非标准端点"方案，PRD 不约束具体技术。
- **理由**：需求定位为"仅用户可创建房间"的本地娱乐/研究工具，无多端联机、无多用户、无云端同步诉求，去后端可大幅降低部署与合规成本。

### D2 叫分规则（叫地主 / 抢地主 采用哪种）
- **决策：采用"叫分制"（非抢地主二次加价）。**
- **流程**：
  1. 发牌完成后，从随机一名玩家开始，**按固定顺序（如逆时针）**依次叫分。
  2. 每人每轮仅一次机会，选项为：**叫 1 分 / 2 分 / 3 分 / 不叫（Pass）**。
  3. 叫分必须**严格递增**（只能叫比当前最高分更高的分，或不叫）；最高叫分者成为地主。
  4. 若首轮三人全部"不叫" → 重新发牌（见 Q4），不进入底牌分配。
  5. 地主确定后立刻明牌（见 D5），获得 3 张底牌（手牌 17→20）。
- **不采用"抢地主"**：即不做"反抢/加倍"二次竞价，以保持规则简单、提示词易组织、与底分直接挂钩。

### D3 积分结算规则
- **底分**：取叫分阶段"最高叫分"作为本局底分（叫 3 分→底分 3；若因全不叫重发后强制首叫者叫 1 分，则底分 1）。
- **倍数（初始 ×1）**：
  - 每个**炸弹** ×2；
  - **王炸**（双王） ×2；
  - **春天**：地主出完且两农民均未出过任何牌（地主春天）×2；或某农民方出完且地主仅出过底牌/未出过主动牌（反春天）×2。
  - 倍数可叠加（如 2 个炸弹 + 王炸 = ×8）。
- **结算公式**：单局基础分 = 底分 × 倍数。
  - 地主胜：两农民各输「基础分」，地主得「基础分 ×2」。
  - 地主负：地主输「基础分 ×2」，两农民各得「基础分」。
- **范围**：每局独立结算；累计战绩为 P1 统计项（REQ-P1-3），不影响单局。

### D4 AI 决策超时与倒计时的关系
- **AI 决策硬超时**：每个 AI 回合设硬超时（**建议 8 秒**，具体由架构/工程定），超时未返回或返回非法 → 触发兜底策略（REQ-R8）：优先尝试出"最小合法牌"，若无合法牌则"过牌（不出）"。
- **玩家倒计时**：仅约束**人类玩家**回合，建议 **30 秒**；归零处理——首版为"自动过牌（不出）"，完整"自动托管出最小牌"列为 P1（REQ-P1-1）。
- **二者关系**：倒计时=人类玩家约束；AI 超时=AI 自身约束，两者独立、互不触发。AI 回合不在牌桌显示"玩家倒计时"，但思考日志面板显示"XX 思考中…"状态，避免界面空窗。
- **提示词要素（交给 AI 模块）**：须包含——我的手牌（含是否已地主）、当前地主、上家/下家手牌剩余数、最近一手出牌（含是否"过"）、本回合是否"必须压过"、剩余炸弹数、当前倍数、规则简述、输出格式要求（JSON：{action: 出牌/过, cards: [...] , reason: "..."}）。

### D5 "明牌底牌"展示时机
- **决策：底牌在"叫分结束、地主确定"后立刻明牌**，三张底牌翻开并常驻展示于牌桌"明牌区"直至本局结束；地主手牌由 17 张变为 20 张同步展示。
- **不在叫分阶段提前展示**（防止信息泄露影响叫分公平）。
- 底牌归属：地主获得 3 张底牌计入其手牌与胜负/倍数计算。
